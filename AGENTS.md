# fence-designer

Fencing scoping tool (GitHub Pages). The canonical spec for this repo lives in `SPEC.md` alongside this file. Feature context: `secureworks-docs/features/fencing-scoping-tool.md`.

Single-file app: everything lives in `index.html` (~16.5k lines). `window.app` is the app object (`var app = window.app = {...}`); integration hooks live in the same file inline. The cloud/GHL layer sits alongside it in `cloud.js` (`window.SECUREWORKS_CLOUD`: `auth`, `ghl`, `ui`) and `integration.js` (`window._swIntegration`) — neither is covered by `SPEC.md`, which specs the design/calculation tool only. The inline price overlay runs before bottom-of-page `cloud.js`, so it must defer its first DB read until cloud initialisation; `npm test` covers live-table and truthful fallback labels at the iPad viewport.

## Client quote render architecture

ONE function renders BOTH the sent PDF and the interactive HTML client quote:
`app._buildFenceQuoteHTML(d, imgs, opts)`. `opts.forPDF` only swaps page geometry (`body.pdf` fixed 794x1123 A4 vs `body.web` responsive); it does NOT change the scope/price/description markup. So a change inside this function applies to both outputs automatically.

- PDF path: `_renderFenceQuoteHTMLToPDF` calls it with `forPDF:true`, then html2canvas rasterises each `.pgwrap > .page` at a FIXED 794x1123 with `overflow:hidden`. There is NO auto-pagination: content that overflows a page is CLIPPED. Respect the per-page vertical budget when adding to a page.
- Web path: `generateFenceWebPreview` (preview) and the send flow (`executeSendQuote`, ~line 14970) call it with `forPDF:false` and upload the result as `html_url`.
- Page order in output: `p1`(cover) + webCtaBar + `p2`(design) + `pSite`(optional site photos) + `p3`(#pgScope, scope) + `p4`(#pg4, investment) + `p5`(terms) + `p6`(close).

Data pipeline: `_collectOutputData()` (raw engine output: totals, line-item arrays, job) → `_gatherFenceQuoteData(rawD)` (the presentation object consumed by `_buildFenceQuoteHTML`, i.e. `d`). All three render callers go through `_gatherFenceQuoteData`, so surface any new render field THERE (it does not pass `job` through; `d.job` is not available inside `_buildFenceQuoteHTML`). Do NOT change the calculation builders `_buildFenceScopeOfWorks` (scope data) or `buildPricingJson` (pricing) — only how their output is rendered. `d.priceLineItems` (client-facing sell rows) is built in `_gatherFenceQuoteData` from the raw engine fields and reconciles to `d.subtotal` (ex GST). In `'itemized'` mode the page-4 table foots with `d.itemizedSubtotalStr` (the exact cent-sum of the displayed line amounts) and `d.itemizedGstStr` (`d.totalStr` minus that subtotal), NOT `d.subtotal`/`d.gst`, so the shown Subtotal + GST always equals the unchanged canonical `d.totalStr` without per-line rounding drift.

Persisted quote settings live on `this.job.quote` and are written via `app.updateQuote(field, value)` (calls `save()`), e.g. `customDescription`, `customLineItems`, `priceDisplay` (`'total'` default | `'itemized'`).

Page-4 budget note: in itemized mode the line-item table can fill the fixed-height page, so the dollar cost-split cards (`splitBlock`) are suppressed there to avoid clipping the PDF. Every party's name still appears on the cover (D5); the per-party dollar split is a deferred slice. In `'total'` mode the split cards are unchanged.

Scope pagination note: the scope section (`.swscope` pages, class-based so it can repeat) renders at a readable but CONDENSED type scale and reads as ONE clean block. In `_buildFenceQuoteHTML` a height estimator (`pagesStages`, `investOnOwnPage`) decides layout: (1) if all stages + the investment block (under-scope total + Included strip) fit one page, they go on one page with the total directly under the scope; (2) if all stages fit but the total does not, ALL stages stay on one page and the WHOLE investment block flows onto its own continuation page as a unit; (3) only if the stages themselves overflow one page do they break, at a BALANCED point between stages, and a lone trailing stage is pulled back so a single stage never floats alone on the next page. Each stage is a `.scope-table` row. Page numbering is dynamic (`pfn`, `nScopePages`, `_pInvest`/`_pTerms`/`totalPages`). Estimator constants (`_estStage` char-per-line, `_USABLE`, `_EST_INVEST`, etc.) are calibrated to run slightly HIGH vs real rendered height (so a "fits" verdict never clips) against the condensed `.swscope` CSS; if you change the scope type scale, re-measure per-page `scrollHeight - 1123` in headless Chrome (must be <= 0 on every scope page) and re-tune. Terms (`#pg5`): a strong pro-SecureWorks clause set (`_termsClauses`) rendered as `break-inside:avoid` `.termgrp`s that CSS auto-balances into two columns (`column-count:2`); clause bodies go through `E()` so use a literal `’` (not the `&rsquo;` entity, which would double-escape). Cover: shared-boundary jobs (`d.boundaryParties.length >= 2`) list all parties equally (name + address, recipient gets a muted "(you)"); single-party jobs keep the detailed `.clientblock` (site/phone/email/issued).

## Material order + work order engine (NOT the client quote; `business_rules.js` is dead)

The supplier **material order** and the internal **work order** are plain-text/HTML outputs built in `index.html` by `_generateMaterialOrderHTML(d)` / `_generateWorkOrderHTML(d)`, fed by the same raw engine object `d = _collectOutputData()` that feeds the quote. `business_rules.js` is NOT loaded by `index.html` (only `cloud.js` + `integration.js` are) — it is effectively dead; do not edit it expecting an effect. `_collectOutputData()` is the material/cost calc engine — its `internalCost`/`materialMargin` are internal only (the client-facing pricing JSON is `buildPricingJson`, unchanged by margin edits).

- **Custom line items** (`job.quote.customLineItems`, min-3 slots, `+ Add`/`Remove` via `addCustomItem`/`deleteCustomItem`) carry a `kind` and a `costPrice`. `_collectOutputData` maps them through `js.custom` → `d.customItems`; **material**-flagged items render a `CUSTOM MATERIALS:` block on the order, labour ones do not, and every item's `costPrice` feeds `internalCost` (`customCostTotal`) so margin reflects cost, not just sell.
- **`kind` is resolved ONLY through `app.customItemKind(c)`, and an ABSENT `kind` means labour** — every mapper, `buildPricingJson` and the UI picker read it, so the control can never claim Material for an item the order treats as labour. That rule is safe only because every blank slot the app creates is stamped material by `_blankCustomItem()`/`_blankCustomItems()` (`init`, `renderQuote`'s fallback, `updateCustomItem`'s create+pad, `addCustomItem`, `deleteCustomItem`'s pad, and the `jobSettings` migration) — so a `kind`-less item is positive evidence the job was saved BEFORE this branch, back when main had no `kind` field and no `CUSTOM MATERIALS` block at all, and those items are the "Extra labour, skip bin" lines a panel supplier must never be asked to quote. Add a new blank-slot site and it MUST go through the helper. Pinned by `tests/material-order-playwright.spec.js`: "a default custom slot on a fresh job reaches the supplier order untouched" (fresh slot ordered + legacy half), "a legacy custom item with no kind never reaches the supplier order", "the kind picker shows what the order will actually do with the item".
- **Plinths are width-aware.** A plinth under a long panel (`getPanelW(panel) > getPanelWidthMm()`) is a LONG plinth: `d.totalPlinthsStandard`/`d.totalPlinthsLong` split the flat `d.totalPlinths`, the order prints separate `PLINTHS (standard)` / `PLINTHS (long)` lines, and margin reads `COST_PRICES.plinthLong` ($48) for the long ones (previously dead).
- **`updateSupplier` must never stomp a chosen buy-from supplier.** The Panel System dropdown fires on EVERY touch (including switching away and back to fix a misclick), so the auto-select only writes `installation.supplierSource` when it is unset or still equals the PREVIOUS panel system's default. An unconditional write silently re-routed the order email to a supplier the operator did not choose — worst on Metroll, the one system with a real alternative. Any test for this has to change the panel system AGAIN after the override; overriding once and stopping cannot see it. Pinned by `tests/supplier-routing-playwright.spec.js`: "a deliberate Buy From override survives later Panel System changes" and "auto-select still re-defaults for an operator who never overrode it".
- **Panel system and buy-from supplier are TWO different fields — never conflate them.** `job.supplier` is the **panel system** despite its name: it keys `SUPPLIER_PROFILES` and drives panel width + the profile list (`<select id="supplier">`, labelled "Panel System"). `job.installation.supplierSource` is **who we buy from** (`<select id="supSelect">`, labelled "Supplier (Buy From)") and it alone decides where the order email goes. Do NOT rename `job.supplier`; saved jobs depend on it. Read it through `app.getSupplierSource()`, which prefers the operator's stored choice and falls back to `PANEL_SYSTEM_DEFAULT_SUPPLIER[job.supplier]` so jobs saved before the buy-from field existed still route — EXCEPT for the `'__custom__'` sentinel, which resolves to `''`: a Custom supplier that has not been named yet must never inherit another supplier's real address, so routing answers an empty `to` with `known:false` and `emailMaterialOrder` refuses to draft (`app.isCustomSupplierPending()`). Opening a draft never writes `supplierSource` back. `d.supplier`/`d.panelSystem` = panel system, `d.supplierSource` = buy-from, `d.orderRouting` = `{supplier,to,cc,known}`.
- **Panel-system profiles** live in `SUPPLIER_PROFILES` (top of the inline script); adding one there auto-wires the installation dropdowns and `getPanelWidthMm`/`getPanelW`. A panel system missing from this map silently falls back to 2380mm — ground new widths in `SPEC.md`, never guess. Widths are deliberately APPROXIMATE (Captain: standard counts as 2.4m, long as 3.1m); there are no per-profile widths, and Stratco's 3150 long width has no published Stratco source.
- **Order-email routing** lives in `SUPPLIER_SOURCES` (name → `to` + supplier-specific `cc[]`) plus `MATERIAL_ORDER_UNIVERSAL_CC`. Array order IS the dropdown order. `getMaterialOrderRouting()` always appends the universal CC, so Stratco carries two. An unknown/custom supplier resolves with an empty `to` — honest, never a guessed address.
- **The material order email is ALWAYS a draft, never a send.** `emailMaterialOrder()` builds a `mailto:` and hands it to `_openMailDraft(url)` — the ONE place this app touches a mail client, and the seam tests stub. Outlook supplies the operator's own signature, so never write one into the body. There is no mail transport in this repo (no backend mail command, no Graph credentials); do not add an automatic send path. A `mailto:` is length-capped by the OS (`_MAILTO_SAFE_LEN`), so `_buildMaterialOrderText` uses ASCII rules — a `═` costs nine characters percent-encoded — and an over-long order falls back to a covering note with the full text on the clipboard rather than being silently truncated.
- **The outbound email body carries NO internal cost.** `_buildMaterialOrderText(d, { forEmail: true })` omits the cost annotations (`plinthLongCost` on the long-plinth line, per-item `costPrice` on custom materials). Exactly TWO call sites pass that flag, and both are things a SUPPLIER receives: `_materialOrderEmail` (the mailto body) and `_generateMaterialOrderHTML`, which builds the hidden `#supplierOrderBody` behind the page's "Copy for supplier email" button. Everything else calls the builder bare and keeps the annotations for internal reconciliation — including the page's visible `<pre>` and its "Copy (internal — includes costs)" button, so the Material Order page carries BOTH bodies, side by side, and which clipboard button was pressed decides which one the operator holds; the internal one's LABEL is what stops it being pressed on the way to a supplier email, so keep it self-describing. The failure a future edit walks into: add one more cost note to the shared builder and it is silently disclosed to the vendor — gate any new cost text on the same flag. The same rule governs what the app POINTS the operator at: when the clipboard write fails AND the order is over length, the covering note and toast name "Copy for supplier email", never the internal Copy button. Pinned by `tests/material-order-playwright.spec.js`: "Task A — the emailed order carries no cost figures, while the on-screen order keeps them", "Unit 4 — with the clipboard denied, the over-length fallback names a cost-free route", "the material order page marks which copy button carries internal cost".
- **`buildPricingJson` line items carry `supplier_name` from the PANEL SYSTEM** via `SUPPLIER_NAME_MAP`, not the buy-from supplier. That is a known mismatch, deliberately left alone: those strings match records in the live Supabase supplier table (`R&R Fencing`, `Metroll`, `Lysaght`, `Stratco` all exist; `RnR Direct`/`Metroll Direct` do not), so changing them is a backend/Captain decision, not a local edit.
- **Profile artwork resolves in three tiers** in `_getProfileSVG(profile, panelSystem)`: repo-held product photography in `app._PROFILE_PHOTOS` (keyed `'<panel system>::<profile>'`, relative `textures/` paths — this ships to Pages under a subpath) → the remote `steelselect.com.au` URL map → the generated `_buildProfileSVG` diagram, which is also the `onerror` fallback. Add a key only when the file actually exists. All four Stratco profiles have a photo, normalised to a 720x470 canvas; they render at `_PROFILE_PHOTO_MAX_W` (520px) rather than the diagram's 340px because CGI Corrugated and CGI Mini are the same corrugated shape at different pitch and are indistinguishable at thumbnail size — picking the wrong one is a wrong material order.
- Coverage: `tests/material-order-playwright.spec.js` and `tests/supplier-routing-playwright.spec.js` (both in the `playwright.config.js` `testMatch`).

## Per-component fence colours (2026-09)

Sheets, rails, posts and plinths each carry a colour. `job.colour` **is the SHEET colour** and is read in ~48 places (quote, order, work order, 3D render, pricing) — it was deliberately NOT rewired. The other three are additive, optional overrides:

- `job.componentColours = { rails, posts, plinths }` — job-level; `run.colours = { sheets, rails, posts, plinths }` — per-run. Both store only what was explicitly set and are **deleted** when cleared, so a job that never used the feature carries none of these keys and behaves identically to before (proven byte-identical across order, work order, quote HTML, specs, pricing JSON and totals).
- Resolve through `app.getComponentColour(component, run)` / `getRunColourSet(run)` — never read the raw fields. Precedence: **explicit run > explicit job > that run's resolved sheet colour**. So overriding a run's sheets does not drag away a rail colour the operator set at job level; the run-override UI labels each blank option with what it actually inherits.
- **Colour never touches price** (Captain: "nah"). Nothing in this feature feeds costing.
- Downstream, differing colours must SPLIT order lines or we buy the wrong stock: `postGroups` keys include sheet/rail/post colour, and `plinthGroups` tallies plinths by colour × width alongside the unchanged flat `totalPlinths*`. The order prints one `Colour:` line when sheets/rails/posts match (byte-identical to before) and expands to `Sheets:`/`Rails:`/`Posts:` only when they differ. The quote adds a single `Trim Colours` spec row only when something differs, protecting the fixed PDF page budget.
- **A group is keyed by spec + colour, never by RUN**, so nothing in `postGroups` maps Basalt stock to Run B. The two documents a person physically handling the job carries — the work order's per-run headings and the material order's `RUN BREAKDOWN` — therefore render `app._runColourText(d, runDetail)` over the `sheetColour`/`railColour`/`postColour`/`plinthColour`/`uniformColour` stamped on each `runDetails` entry. It returns `''` unless `d.componentColours.uniform === false` (the job genuinely carries more than one colour ON THE ORDER) and the run actually put panels on it, and it names a plinth colour only when that run actually has plinths — so a single-colour job renders both documents byte-identically, a panel-less run names no colour, and a run with no retaining names no plinth colour.
- **`uniformColour` deliberately means two DIFFERENT things and the two must stay apart.** On a `postGroups` row it is sheets/rails/posts ONLY, because plinths are their own order line and do not belong on a panel line. On a `runDetails` entry it is FOUR components (plinths included, unless the run has none), because a run whose only difference is its plinth colour must still be named on the crew documents — with a three-component test it reported uniform and both runs printed the same information-free colour. `_postGroupColourText` and `_runColourText` are correspondingly separate renderers; do not collapse them back into one.
- **The colour summary is derived FROM those groups, never from the job model.** `_summariseComponentColours(job, postGroups, plinthGroups)` reads `postGroups[].sheetColour/railColour/postColour` and `plinthGroups[].colour`, so the quote can never name a colour the order does not buy — a run with no panels never entered `postGroups`, a gate-only job has none, a job with no retaining has no `plinthGroups`, and a component overridden on a job carrying none of that component contributes nothing. A job with nothing on the order at all falls back to `job.colour` for every component, so the quote is neither blank nor claiming trim that does not exist. Do not reintroduce a job-model walk here or add a compensating filter; both diverge from the order again. Pinned by `tests/component-colours-playwright.spec.js`: "a colour set for stock the job does not carry never reaches the quote", "a run with no panels yet does not put its colour on any quote surface", "no rendered surface names the job colour once a component colour overrides it".
- **Every HUMAN-RENDERED colour resolves through `app.resolvedSheetColour(d)`** (or `primarySheetColour(d)` where only one colour can be shown, e.g. a swatch) — never `d.colour` directly, because `d.colour` is the job DEFAULT and a run can override it. That covers the client quote (specs, lede, scope-of-works, itemized line labels), the material order, the work order, the PO card, the cost breakdown, the Material Verification checklist and its Quote Preview panel, the `pricing_json` descriptions, and both jsPDF paths. Per-run surfaces read the resolved colour carried on `runDetails[].sheetColour` / the `pricing_json` run's `sheet_colour`; per-group surfaces use `_postGroupColourText` / `_plinthGroupRows`. Four review rounds were spent closing this class one site at a time — add new surfaces to the helper, not to `d.colour`.
- **Two deliberate exceptions.** GATES resolve through `app.gateSheetColour(d)`, which takes the ORDER'S single sheet colour when there is exactly one (so a run override that moved the whole job off `d.colour` still buys a matching gate) and falls back to the job-level `d.colour` only when runs genuinely differ — nothing attaches a gate to a run, and `resolvedSheetColour` JOINS colours, which on a supplier order line is unfulfillable stock. What a gate SHOULD be on a job whose runs genuinely differ is deferred product work. Pinned by `tests/component-colours-playwright.spec.js`: "a gate is ordered in the colour the order actually buys, and never two" and "no material order line ever names two colours at once". The 3D render, the Profile View and the AI image prompt still use `job.colour` (sheets) only — neither trim colours nor a per-run sheet override is visualised.
- **Operator text in an inline handler argument needs `_escJsAttr`, not `_esc`.** `_esc` does not escape the apostrophe, so a value interpolated raw into a single-quoted JS argument makes the whole handler a syntax error and the control silently inert. Its only live consumers are `_getProfileSVG`'s two `onerror` handlers, where the value is the operator-typed custom PROFILE name (`_addCustomOption('profile', …)` → `updateProfile`). No COLOUR reaches a handler any more: every handler in the colour UI interpolates only generated run ids and `FENCE_COMPONENTS` constants.
- Coverage: `tests/component-colours-playwright.spec.js`.
- **Internal cost never reaches the client quote.** `_gatherFenceQuoteData` is a hand-built whitelist, not a passthrough of the raw engine object, so `costPrice`/`kind`/`internalCost`/`materialMargin`/`customCostTotal` cannot reach `_buildFenceQuoteHTML`. Pinned by `tests/supplier-routing-playwright.spec.js` ("cost, margin and internal fields never reach the client quote HTML") — keep that whitelist a whitelist. Scan the quote with base64 data URIs stripped: embedded images coincidentally contain almost any short digit string.

## Launch modal, lead search and the repeat-client new job (2026-07)

The launch modal (`index.html` ~2237) offers four options: (1) Load GHL lead/contact → `_swIntegration.searchLeads('')`, (2) Resume draft, (3) Start new local draft, (4) **New job for existing client/lead** → `_swIntegration.searchLeads('', { mode: 'new_job' })`. Option 4 is the explicit repeat-client path. For fencing it resolves history first, then calls the authenticated `mint_fence_job` server command with `DELIBERATE_REPEAT`; browser-side contact/opportunity/job minting remains forbidden.

- **`ghl.searchLeads(query, pipeline, opts)` (`cloud.js`) is the one search entry point.** It hits the fast `lead_search` edge action (contacts-first + parallel opp lookup) and falls back to the LEGACY `search` action if `lead_search` isn't deployed, so a Pages build can never outrun the edge function. The fallback only goes sticky for the session (`_leadSearchUnavailable`) once the backend CONFIRMS the action is missing (`_unknownActionSignal` → `'confirmed'`); an ambiguous failure (`'maybe'`) falls back for that call alone and needs `_LEAD_SEARCH_MISS_LIMIT` (2) CONSECUTIVE misses on the SAME query to latch, and a 404 (`'soft'`) never counts. This matters because the legacy path cannot return contact-only rows. `opts.signal` aborts a stale in-flight request. The separate `ghl.search(query)` is a different, legacy call still used by the job-relink path (`cloud.js` ~1612) — do not conflate it with `searchLeads`.

A contact-only row has no opportunity to load, so fencing sends it through the guarded `RESOLVED_NO_JOB` mint path. `lookupFailed` rows remain dimmed and unselectable.

Create selections lock the modal until the guarded owner settles. Ambiguous identity/checkpoint failures are deterministic safe stops; transient server-mint failures retain the persisted request UUID for an idempotent retry.
- **Fencing `_startNewJobForContact(row, permit)` consumes only the canonical result already returned by `_enterJob`.** It never calls legacy `createContactAndOpportunity` or `createJobForOpportunity`. A canonical result with `revision.requiresLoad` routes through the direct-link owner unless the operator explicitly chose keep-current; that preserves existing/frozen scope rather than opening a blank editor. The legacy helper body remains for non-fencing tools only.
- **The inline client-name autocomplete is the second entry to the same flow.** Contact-only rows are selectable and call `_swIntegration.startNewJobForContact`; lookup failures stay filtered/inert. Keep its fixture in `tests/entry-funnel-inline-autocomplete-evidence.js` aligned with the lead modal.

## M4 frozen-revision / QA / media gotchas (verified 2026-07)

- **Sent-job reopen is intentionally read-only.** `integration.js` `_autoLoadJob` (G-F1) redirects a job with `latest_frozen_scope_revision_id` to the `?scope_revision_id=` frozen viewer; that viewer sets `_isReadonly` (mode `readonly` **or** any `scope_revision_id`), which makes `save()`/`saveAfterSignOff()` bail with reason `readonly`. This input-lock is BY DESIGN — do not remove it. Editing a sent scope goes through the "Make a revision" clone flow only.
- **The frozen viewer must still LOAD media.** `_autoLoadFrozenRevision` must call `_loadCloudMedia(_jobId)` so the sealed job's site photos + video are viewable/downloadable in read-only mode. (It historically skipped media, hiding the scoper's docs on reopen.) Media load is a pure read; `_isReadonly` still blocks all writes.
- **`window.fenceQA` must be wired.** QA verification round-trips through `scope_json.verification`: `getFencingState()` reads `window.fenceQA._verificationState` on save; `loadFencingState()` restores it on reopen (`integration.js` ~690/~701). The QA object is declared `const fenceQA` in `index.html`, which is NOT a window property — so `index.html` must explicitly `window.fenceQA = fenceQA;` (right after the object, ~13415). Without it the round-trip silently no-ops (verification saved as `null`, never restored), and a reopened/sent job loses QA and re-demands sign-off. Patio uses a top-level `var patioQA` and relies on the same `window.patioQA` bridge.
- **Every reset path MUST go through `_resetToolMediaState()`, never a hand-rolled copy.** `window.sitePhotos`/`window.siteVideo` are globals that `app.init()` does not touch, so a reset without it leaves the PREVIOUS client's media in the queue — load paths only mask this by calling `_loadCloudMedia` straight after, and the repeat-client path creates an empty job and loads nothing. It also clears `_bgUploads` (a surviving `'__video__'` entry makes `_startBgVideoUpload` skip the next job's video), cancels `_videoRetryTimer`, and bumps `_mediaEpoch`. It is tool-agnostic — fencing and patio both route through it. `_openFencingTargetSeparately` and `_resetPatioForm` call it internally. `_openFencingTargetSeparately` now THROWS `checkpoint_failed` when a dirty fencing draft cannot be checkpointed AND verifiably read back (`_checkpointLocalDraftBeforeLoad` + `_verifiedFenceCheckpoint`); that throw happens before any reset, so callers must treat it as a safe stop that leaves the scope on screen — never swallow it. Paths that own their own reset sequence (`startLocalDraft`, `resetJob`) call `_swIntegration.resetToolMediaState()` directly. paths that own their own reset sequence (`startLocalDraft`, `resetJob`) call `_swIntegration.resetToolMediaState()` directly. Conversely, any path that RESETS then links an existing job must reload media (`_swIntegration.loadCloudMedia(jobId)`) or the grid sits empty and QA re-demands capture on a job that already has photos.
- **`_mediaEpoch` is how a deferred video upload tells a job SWAP from a promotion.** `_startBgVideoUpload` captures the epoch at upload START (not in the rejection callback); the success path, the failure path and the retry timer all bail if `_mediaEpoch !== epoch`, so a reset mid-flight can't spend the new job's retry budget, report the old video's outcome on the new job's status channel, or upload the previous client's walkthrough. A `local-` id walking up to its real cloud id is the SAME draft, so only an intervening media reset invalidates a retry.
- **Frozen-viewer chrome must be torn down when a job leaves the viewer.** `_clearFrozenViewerChrome()` removes both banners and gives back the body padding each reserved (tracked on `banner.dataset.swPadTop`). The banner's "Make a revision" button and revision switcher close over the OLD revision/job, so left mounted on the repeat-client's new editable job they would clone the previous client's sealed scope. `_startNewJobForContact` also clears `_isReadonly` + the `readonly-mode` class, since its URL drops any `?scope_revision_id`/`?mode=readonly`.
- **Neighbour cost share % is mandatory before quote generation and send — and ONLY those.** It lives behind `app._validateRequired({ forQuote: true })`, which `showSendQuoteModal` and `generateQuotePDF` pass; the material order, order email and work order call `_validateRequired()` bare and stay reachable, because the crew often must order stock before a neighbour's share is settled. Put any future client-billing rule behind the same flag. It is mirrored as a RED `fenceQA.runScopeChecks` item (QA sign-off gates the send door only). A share of 0 counts as missing, because every downstream consumer writes `n.sharePercent || <default>` and would silently substitute its own number. The input renders empty with a placeholder when unset — it used to render an even-split default it never persisted, which is how jobs reached Send with no share stored. The copy in dead `validateForScopeComplete` is kept in step but enforces nothing.
- **Send/freeze does NOT hard-require a complete checklist.** The QA wizard (`runScopeChecks` in `index.html`) blocks outputs only on RED items; photos are RED only at **zero** (≥1 is fine), and <5 photos / unfinished video are AMBER (acknowledge-only). So a scope can freeze with an incomplete checklist. `validateForScopeComplete` (~13206, its "≥1 site photo" rule at ~13225) is dead code — no call site. Consider a harder pre-freeze gate as a follow-up.

## Scope-save reconciliation (compare-and-save, 2026-07)

Every scope write is compare-and-save: the client sends the server-issued cursor (`baseScopeHash` + `scopeCursorJobId`) and the server rejects a stale or foreign write with a typed 409. The seam lives in `cloud.js` (`saveScope`, `_runAutoSave`, offline flush) and `integration.js` (`_rememberScopeCursor`, `_attachScopeSaveCursor`, `_handleScopeSaveError`).

- **The cursor is only trusted when it is provably ours.** `_attachScopeSaveCursor` attaches `baseScopeHash` ONLY when `String(_scopeCursorJobId) === String(_jobId)`; `cloud.js` re-checks the same thing before replaying a queued action and strips the cursor (quarantine) when it does not match. A cursor from a previous job must never be spent on the current one — that is how a scope gets overwritten across clients. `_rememberScopeCursor` therefore writes the hash and its owner as ONE unit (an owner-less hash is dropped entirely), and every path that drops `_baseScopeHash` (reset, `local-` id, `_connectJob` clear) must also null `_scopeCursorJobId`. When two queued saves for the same job coalesce, `_mergeSaveMeta` takes hash + owner from the SAME source meta and re-derives `cursorQuarantined` against the queued job id, so an owned cursor cannot inherit an earlier stripped cursor's flag.
- **`_flushAttempt` / `_autoSaveAttempt` are transport-only meta flags** and are deleted before the request body is built. `_flushAttempt` marks an offline-queue replay: it must not be re-queued or auth/transport-retried (it is already the retry). `_autoSaveAttempt` marks the timer-driven save and is what lets a transport failure escalate to the bounded retry budget instead of silently queueing.
- **The only silent, automatic retry is proven-empty-server-scope adoption** (`_provenEmptyServerScope`, plus a `missing_scope_cursor` whose payload is byte-identical to the server's). Everything else stops and asks: `scope_ref_mismatch` hard-stops (wrong job identity, retain local), genuine divergence stops for exactly one keep-iPad/take-server choice, and an unreadable/absent server `scope_json` is treated as UNKNOWN — never as "take server".
- **Recovery is fencing-only.** `_handleScopeSaveError` returns false for any other `_toolType` (the cursor plumbing and `_verifiedFenceCheckpoint` are fencing-specific), handing the error back to the pre-existing path instead of opening a modal with no working branch. A manual save whose recovery returns false shows the conflict message and keeps the draft local — it must not report "saved".
- **An edit must not unblock a conflict stop.** `_runAutoSave` clears `ctx.blockedReason` on a fingerprint change only for `transport_exhausted`/unset; a conflict reason stays latched until the user resolves it, otherwise typing would loop the same rejected save forever. A blocked fingerprint still RE-SCHEDULES the timer (polling locally for edits, sending nothing) — killing it would strand the transport budget reset. The recovery banner's "Retry sync" button is shown only for `_RETRYABLE_RECOVERY_STATES` (transport/server-check kinds); a latched conflict gets no retry, since re-arming would re-send the payload the server already rejected.
- **A queued save carries WHY it queued.** `_queueScopeSave(..., queuedReason)` stamps `'offline'` (default) or `'server_error'` on the returned job, the `job:saved_local` event and the `autosave:queued` event; `integration.js` branches on it so a 5xx/408/429 reports "Server rejected the sync — saved on iPad only" instead of the benign pending-sync copy. Do not collapse the two — they mean different things to the scoper standing on site.
- **A mid-flight job swap retires the autosave context.** After `await saveScope`, `_runAutoSave` returns immediately if `ctx !== _autoSaveContext` (both success and catch paths) so a stale save cannot write the new job's cursor, status or blocked state. The queued-payload discard is the one thing that still runs, since it is scoped to `ctx.jobId` + payload — and it runs ONLY when the response was not itself queued, or a genuine queue entry would be dropped.
- **Recovery must never write before the local draft is safe.** `_verifiedFenceCheckpoint` writes and reads back a `fenceJob_checkpoint_<localDraftId>` snapshot; it returns true (nothing to protect) when there is no meaningful local draft, false only on a real write failure — a false verdict aborts the branch with nothing written.

## localStorage sweeps must not evict the Supabase session (2026-08)

`app._cleanupStorage()` (`index.html`) is a DENY-BY-DEFAULT sweep: anything not on `keep`/`keepPrefixes` is deleted. It runs under quota pressure from `save()`'s QuotaExceeded recovery and from `_writeLocalDraftCheckpoint`'s `cleanupFirst` attempt (which sits inside the mint preflight), so a fat linked job makes it fire repeatedly. `keepPrefixes` therefore includes `'sb-'` — the Supabase auth keys. Dropping it evicts the signed-in session, after which `authorizedHeaders` (`cloud.js`) silently downgrades every request to the shared key and only `mint_fence_job` (the one JWT-only server action) fails. Any new key that must outlive a sweep has to be added here. Covered by `tests/session-eviction-harness.js`, including a static pin on the prefix list.

The shared-key fallback itself is deliberate (field sync must never hard-block), so the mask is killed rather than the fallback: a downgrade while `_user` is set emits `auth:session_lost`, the header badge LATCHES signed-out on it (a repaint from the cached `_user` cannot flip it back, and its click routes to login, not the sign-out confirm), and `ghl.mintFenceJob` pre-checks a REAL session and fails fast with operator-readable copy instead of surfacing the server's 401. The latch clears only on `auth:session_restored`, emitted on the lost→restored transition when a Bearer token attaches again or `SIGNED_IN`/`TOKEN_REFRESHED` fires — the cached `_user`/`isLoggedIn()` are never cleared on loss. While the latch is set, `ui.showLoginModal` must NOT take its already-signed-in auto-close (which trusts that same cached `isLoggedIn()`) — otherwise the login the badge just routed to dismisses itself and the tap is dead.

## Send-quote must save fresh pricing to the cloud before calling prepare_quote (2026-08)

`secureworks-backend` `send-quote/index.ts`'s server-side pricing gate (`quotePricingGateError`) reads `jobs.pricing_json` straight from the database at send time, NOT anything this tab just computed — so fence-designer must guarantee that column is fresh before it calls `prepare_quote`/`send`/`send-runs`. Material Verification's confirm (`_mvConfirm`, `index.html`) only calls `app.save()`, which is localStorage-only; the DB write otherwise depended on the lagging 30s autosave tick, or on `showSendQuoteModal()`'s "assign job number" branch — which is SKIPPED once a job number already exists, i.e. on almost every real send. `executeSendQuote()` now awaits `window._swIntegration.saveToCloud({ requireSynced: true })` (which rebuilds `_pricing_json` fresh via `getFencingState()` and round-trips `save_scope`) before any prepare/send call, for both the single-quote and per-run flows. `requireSynced` makes the save FAIL CLOSED: `integration.save()` returns an outcome (`{synced}` / `{queued, queuedReason}` / `{reason}` on its silent stops), and `saveToCloud` throws a `sync_required` error when the scope only queued locally (offline/5xx/auth-downgrade), the save silently stopped (login/validation), or a 409 scope-conflict recovery ran (recovery being handled is NOT the pricing being synced — most recovery branches retain the iPad draft and write nothing), so the send halts with honest copy instead of letting the server gate read a stale total; a readonly viewer is exempt (no local edits — the server copy is already authoritative). Covered by `tests/reported-regressions-playwright.spec.js` ("send-quote saves fresh pricing to the cloud..." plus its two fail-closed companions), which pin the job-number-already-assigned condition, assert `save_scope` precedes `prepare_quote` with a matching non-zero total, and assert that a queued-only save and a 409 scope-conflict recovery each block `prepare_quote` entirely. Diagnosis: fence-designer-qa-quote-zero, 2026-08-14.

## Guarded fencing entry funnel (2026-07)

Every supported fencing launch/load door must invoke `integration.js` `_enterJob(intent, target)` through `window._swIntegration.enterJob`; coverage is in `tests/entry-funnel-runtime-harness.js`. GHL supplies context, while Supabase remains scope-history authority. Unresolved/contact-only contexts call `cloud.ghl.mintFenceJob` only after ambiguity and local-checkpoint checks; duplicate/raw mappings still stop. Cross-job linking goes through `_swIntegration.linkFencingAnchor` (never `app._linkCloudAnchor` directly), which clears old refs, cursors, revision anchors and pending mint ownership before save. Do not restore direct browser mint fallbacks or add a load door around this owner.

- **The seven intents are the whole surface**: `new_local`, `resume_local`, `ghl_context`, `existing_job`, `editable_scope`, `frozen_revision`, `amendment`. Anything else throws `unsupported_entry_intent`. `_enterJob` returns a short-lived PERMIT held in module-private `_activeEntryPermit`; only the most recent permit is valid. `_requireEntryPermit(permit, intents)` gates the sensitive helpers (currently `_startNewJobForContact`), so a raw create/load helper cannot be called from outside the funnel — it throws `entry_funnel_required`. Non-fencing tools get a permit unconditionally; every stop branch below is fencing-only.
- **`ghl_context` resolves identity BEFORE granting the permit.** Ambiguous/failed rows, duplicate Supabase mappings and multiple matching checkpoints stop first. A unique existing job loads directly. Otherwise `_mintFenceCanonical` persists `pendingMintRequestId` before network IO and calls `mint_fence_job` with `RESOLVED_NO_JOB`; explicit option 4 uses `DELIBERATE_REPEAT`, a reason, and sorted existing-job evidence. Lost responses replay the same UUID. Only a complete canonical response clears the pending request.
- **The guarded preflight's canonical id is consumed, never re-resolved.** `loadPicker`, `searchLeads` and the inline autocomplete take the job id `_enterJob` already resolved or minted (stamped on the row as `supabaseJobId`/`_supabaseJobId` and on `permit.target.jobId`) and LOAD it via `cloud.ghl.loadJob`; a second `findJobByOpportunity` here is replication-sensitive and could miss a freshly minted job and orphan it. Non-fencing tools keep the `findJobByOpportunity` load-existing lookup, since `_enterJob` never stamps a canonical id for them. The inline autocomplete resolves contact + loads the canonical job BEFORE the form/media reset, so a load miss stops with the scope still on screen.
- **Entry errors carry `code` (mirrored as `reason`) and an operator-readable message** built by `_entryError`; `_reportEntryStop` is the auto-load catch (clears `_jobLoaded`, toasts, `updateUI()`), and `_restoreCurrentFenceUrl()` puts the URL back to the currently-open job when a URL-driven entry is cancelled or a frozen viewer is declined. `_recordEntry` appends to a capped 40-entry ring read via `_swIntegration.getEntryAudit()` (audit only, grants nothing); `_swIntegration.noteEntryTarget(intent, target)` stamps the id a permitted door actually produced.
- **Launcher option 3 (`startLocalDraft`) is deliberately zero-network and unstoppable.** `new_local` has no fencing stop branch, and the door does NOT await the permit (it only logs a rejection) so the offline path can never be blocked. The real `localDraftId` is stamped afterwards via `noteEntryTarget` — never audit an id that was not created. Adding any stop here means making this call awaited and blocking.
- **Dirty-work handling is explicit at every switch.** `_openLocalDraftCheckpoint` is now `async`: permit → `resolveFencingTargetSwitch` (where `keep_link`/`cancel` both mean "stay on the current draft", since a local checkpoint has no anchor to keep) → verified checkpoint via `openFencingTargetSeparately`. The `?scope_revision_id=` auto-load asks the same question before opening a sealed parent; a frozen target cannot accept `keep_link`, so keep/cancel clears `_isReadonly` + `readonly-mode` and restores the URL. `_scrubLocalResumeJob` (`index.html`) resets `pendingOps`, bumps `identityVersion`, and deletes the cursor/anchor keys (`baseScopeHash`, `currentScopeHash`, `scopeUpdatedAt`, `lastCloudCursorAt`, `scopeCursorJobId`, `scopeCursorProvenance`, `syncAnchorRevisionId`, `keep_link_job_id`) — the same cursor/anchor keys `_scrubCrossJobIdentity` clears, which additionally drops the pending-mint ownership keys (`pendingMintRequestId`, `pendingMintFingerprint`, `pendingMintIntent`, `pendingMintStartedAt`, `completedMintCanonical`).
- **Coverage**: `tests/entry-funnel-runtime-harness.js` proves all doors, ambiguity stops, stable mint UUID replay and ownership scrubbing; `tests/entry-funnel-inline-autocomplete-evidence.js` and `tests/cp2-repeat-client-browser-evidence.js` drive the two create surfaces with stubbed `mint_fence_job`. No test uses live GHL/Supabase.

**Deployment remains separately gated.** Backend PR 341 landed the additive command and contract, but migration/function deployment and production proof are independent approvals. The browser integration must fail closed on typed mint errors, retain the local draft/request UUID, and never fall back to legacy browser minting.
